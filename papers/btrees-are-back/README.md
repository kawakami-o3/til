# B-Trees Are Back: Engineering Fast and Pageable Node Layouts

* 著者: Marcus Müller, Lawrence Benson, Viktor Leis (TUM)
* 掲載: Proc. ACM Manag. Data 3(1), Article 14 (SIGMOD 2025)
* DOI: https://doi.org/10.1145/3709664
* PDF (著者版): https://www.cs.cit.tum.de/fileadmin/w00cfj/dis/papers/btrees-are-back.pdf
* 実装: [btree-cpp](https://github.com/m-mueller678/btree-cpp/tree/sigmod25) (単一スレッド版), [btree24](https://github.com/m-mueller678/btree24/tree/sigmod25) (vmcache 統合版)

## 一言で

可変長キーを扱う、ページサイズ固定 (4 KiB) の B-Tree について、ノード内レイアウトの最適化6種を個別に計測した論文。
さらにノードごとに最適なリーフ形式を実行時に選ぶ「適応型 B-Tree」を提案している。
ページング可能なまま、ART / HOT / Wormhole といったインメモリ専用構造にかなり迫り、条件次第では追い越せることを示した。

## 問題意識

* メモリ価格の低下が止まり、データは増え、NVMe は速くなった (1台で 12M IOPS)。
  その結果、**メモリから溢れても動く索引**がまた重要になった (LeanStore, Umbra, vmcache 系の流れ)。
* ART などインメモリ専用構造はページングできない。ページングに向くのは固定サイズノードの B-Tree。
* なのに B-Tree の研究は**固定長キー前提**のものばかり。実システムのキーは文字列が多い (OLAP の値の約半分が文字列)。
* TLX, Rust の BTreeMap, Google の btree などのジェネリック実装は、可変長キーをヒープに置いてポインタで持つ。キャッシュ局所性が悪い。
* 「現代の CPU で、可変長キーの B-Tree をメモリ上で速くするには、何が効くのか」の定量的な指針がない。

木全体の操作 (split / merge / 走査) と、ノード内の操作 (insert / lookup / delete) は切り離せる。
この論文は**ノード内レイアウト**だけに絞っている。

## ベースライン: スロット付きページ

```
[header][slot][slot]...  →    ←  ...[key|value][key|value][fences]
         スロット配列は前から伸びる      ヒープは後ろから伸びる (bump allocator)
```

* ヘッダ: tag (ノード種別), count, heapUsed, heapStart, upperChild, 下限/上限 fence, prefixLength
* スロット: ヒープ上の offset, key 長, value 長 (各 16bit)。**キー順にソート**されているので二分探索できる
* fence: ノードが担当するキー範囲の下限と上限
* split: 中央値付近の count/16 個を見て、なるべく短い区切りキーを選ぶ
* delete: スロットを消すだけ。ヒープは insert 時にまとめて compaction する
* 隣接ノードの 3/4 以上が空いたら merge

## 6つの最適化

### 1. Prefix Truncation (1977〜)

ノード内のキーはすべて、**両 fence の共通接頭辞**を共有している。だからその部分を落として格納する。

* 例: fence が `https://a` と `https://b` なら `https://` を省く。
  全キーが `a` から始まっていても、上限 fence が `b` なので `a` は省けない。
* 接頭辞は split / merge のときだけ決まり、通常の insert では変わらない。
* 効果は**空間**: urls ではリーフあたりのレコード数が 36 → 96、L1 ミスは scan で 35% 減。
* 比較命令数はあまり減らない。速くなる理由は「密に詰まること」。
* 省ける接頭辞の平均長: urls 49B / wiki 7.0B / dense 2.3B / sparse 1.5B。空間は 7〜64% 減る。

### 2. Heads (poor man's normalized keys)

各スロットにキーの**先頭4バイト**のコピーを持たせる。

* 二分探索の比較がスロット配列の中で済み、ヒープへのランダムアクセスが減る。
* 4バイトを整数として1命令で比較する (memcmp を使わない)。
* スロットは 10B になるが、アラインせず packed で持つ (差は 3% 未満)。
* 効果: lookup / insert が **+16〜64%**。整数キーは head に全部収まるので特に効く。
* 弱点: urls は先頭が似ていて差がつきにくい (隣接キーの head が異なる割合: urls 38%, wiki 61%)。
  root ノードではほぼ全キーが `http` で始まるので役に立たない。
* コスト: 1レコードあたり約 5.7B 増える。fan-out は 8〜20% 下がる。

### 3. Hints (LeanStore 由来)

ヘッダに **16個 (64B) の head を等間隔にサンプリング**した配列を置く。

* まず hints を線形走査して、二分探索の範囲を絞り込む。
* 整数キーの lookup が +25〜26%。文字列ではほぼ変わらない (-0.6〜+6%)。
  head と同じで、先頭バイトで区別しやすいかどうかで効き方が決まる。
* 空間コストは 1.5〜2% と小さい。insert が中心のワークロードでなければ入れて損はない。

### 4. Fingerprinting リーフ (FPTree 由来)

リーフを**ソートしない**。キーの1バイトハッシュの配列を SIMD で線形検索する。

* fingerprint が一致したエントリだけヒープを見るので、文字列キーの lookup が **+13〜22%**。
* insert は末尾に追加するだけで済み、スロットをずらさなくてよい。
* scan の前に未ソート部分をソートして、ソート済み部分にマージする (遅延ソート)。
  このため scan が書き込みを伴うことになり、並行制御が面倒になる。
* 整数キーには逆効果。レコードが小さくて数が多いので、fingerprint 配列自体が多くのキャッシュラインにまたがり、衝突も増える。
* head を持たないので 1レコードあたり約 4B 小さい。

### 5. Semi Dense Leaves (SDL) と 6. Fully Dense Leaves (FDL)

**新規提案**。キーが密な整数 (ID 列など) なら、リーフを「オフセットで直接引ける配列」にする。

* 正規化キーの**末尾4バイト**を数値部とみなす (frame-of-reference)。
  それ以外の部分は lower fence と一致している必要があり、ノード内のキーはすべて同じ長さでなければならない。
* 数値部から基準値を引いた値がそのまま配列の添字になる。**キー比較が不要**。
* SDL: 取りうるオフセットごとに 16bit のスロットを持ち、値はヒープに置く。値の長さは可変でよい。
* FDL: 値も固定長と仮定する (例: 8B の tuple ID)。存在ビットマップと値の配列だけで構成する。4 KiB に約 500 件入る。
* 比較ベースのリーフが split しそうになったときに、変換を試みる。

FDL の split が独特:

* 容量が fence 範囲より狭くても FDL にしてしまう (範囲を「オーバーコミット」する)。
* 範囲外のキーが来たら、中央値で分けずに**新しい空のリーフを右に作る**。
* その結果、昇順 insert のときに左ノードが満杯のまま残り、木が非常にコンパクトになる。

分割元が複数ある連番 ID (パーティション) への対策もある:

* 範囲の境界をまたぐノードは dense にならない。
* そこで「下側のノードが dense にできる最大の分割点」が中央値以上なら、そこで分割する。

効果 (密度 100%):

| | SDL | FDL |
|---|---|---|
| lookup | +37% | +71% |
| insert | +97% | +213% |
| scan | 最大 +16% | 最大 +105% |
| 空間 | -40% | -52% |

* FDL は空きスロットも満杯のスロットと同じだけ場所を取るので、高密度でないと効かない。
  10% 速くなるのは密度 44% から (SDL は 28% から)。FDL が SDL を追い越すのは密度 58%。
* パーティション連番の insert では、FDL が hints 構成の最大約 2.7 倍。SDL は効かない。

## 結果の要約 (lookup への効果)

| | urls | wiki | sparse | dense |
|---|---|---|---|---|
| Prefix Truncation | + | ≈ | ≈ | ≈ |
| Heads | + | ++ | ++ | ++ |
| Hints | ≈ | ≈ | + | + |
| Fingerprinting | ++ | ++ | - | - |
| Dense Leaves | ≈ | ≈ | ≈ | +++ |

* Prefix truncation、heads、hints は**ほぼ常に入れてよい**。
* リーフの形式はキーとワークロードで最適解が変わる → 適応型にする。

## 適応型 B-Tree

リーフ形式を **比較ベース (heads + hints) / Fingerprinting / FDL** の3つから自動で選ぶ。

```
             Fingerprinting
  head が悪く scan が少ない ↑↓ head が良いか scan が多い
              Comparison
         dense にできる ↓↑ できなくなった
                 Dense
```

* **Dense にできるなら常に Dense**。効果がずば抜けているため。
* **Key-adaption** (split / merge のときだけ判定する):
  隣接キーの head が一致するペアの数が全体の 1/16 未満なら「head が良い」とみなし、比較ベースを使う。
  これは「文字列っぽいかどうか」を間接的に測っている。
* **Operation-adaption**: scan と点操作の頻度をリーフごとに 1バイトのカウンタで推定する。
  * scan のたびに 15% の確率で +1、点操作のたびに 5% の確率で -1 する。範囲は 0〜3 で飽和する。
  * 255 は「無効」を表す番兵。head が良いノードではカウンタを無効にする。
  * 文字列キーの場合、fingerprinting で scan が遅くなる分は lookup が速くなる分の約3倍。
    そこで「scan が点操作の 1/3 以上あれば scan が多い」とみなす。この比率が 15% / 5% の確率に表れている。
  * カウンタが端に達したら、読み取り操作の中でもその場で形式を変換する。
    書き込みが一切ないまま lookup 中心から scan 中心に変わるケースに対応するため。
    空き容量が足りなければ変換を中止するので、読み取りが木の構造を変えることはない。
* 閾値や確率を 0.5〜2 倍にしても性能はほとんど変わらない (頑健)。
* 結果: ほぼ全ケースで「その場で最良の固定構成」の 98% 以上の性能が出る。

## インメモリ構造との比較

キー + 値で 300MB、値は 8B。ART / HOT は tuple を別に格納するため、ポインタ経由で持たせて比べている。

* **Wormhole**: ベースラインは lookup で 53〜60% 遅い。適応型でも 26〜28% 遅いが、dense では **27% 速い**。
  insert は文字列なら適応型が 17〜27% 速い。dense では 429% 速い。
* **ART / HOT**: 文字列の lookup は HOT と同等 (適応型比で +5%〜-14%)。ART は 34〜37% 遅い。
  整数は ART が強い (sparse で +129%)。
* **scan は B-Tree の圧勝**: 適応型は trie より 85〜219% 速い。ベースラインでも上回る。
* **TLX** (ジェネリック B-Tree): 文字列はキーが `std::vector` 経由の間接参照になるため遅い。適応型は 148〜259% 速い。
* **空間**: 適応型 B-Tree が全データセットで最小。
  * インメモリ構造は tuple を個別に malloc するので、アロケータのオーバーヘッドと 64bit ポインタが効いてくる。
  * B-Tree はページ単位で確保し、ページ内のレコードを 16bit オフセットで参照するので有利。
  * HOT / LITS / Wormhole の各論文は「索引本体だけ」の空間を測って省メモリを主張している。この論文は tuple の格納まで含めて比べているので、結論が違って見える。
* Zipf の偏りを強くすると、ART / TLX / Wormhole が相対的に有利になる。

## システム統合 (vmcache)

* ノードが固定ページなので、楽観的ロックカップリング (OLC) を使うバッファマネージャ vmcache に、**データ構造を変えずに**載せられる。
* 24スレッドでも、適応型はベースラインに対する優位を保つ。
* メモリから溢れた状態 (バッファ 1 GiB、データ 9〜11 GiB、Samsung 980 PRO):
  * 速さを決めるのは**空間効率**、つまり SSD から読む確率。urls と dense では適応型が大きく勝つ。
  * sparse は head の空間コストのぶん少し負ける。
  * SSD 読み出しは 661k〜777k IOPS で、fio で測った上限の 61〜72%。
* Contention split: ページ単位のロックで生じる競合を、ホットなリーフを分割して緩和する。

## 自分用メモ / 理解のポイント

* **「CPU 時代の B-Tree の最適化 = キャッシュミスを減らすこと」**が一貫したテーマになっている。
  * heads / hints はスロット配列だけで探索を完結させるため。
  * prefix truncation はノードを密にするため。
  * fingerprinting はヒープに触る回数を減らすため。
  * dense は比較そのものをなくすため。
* 同じ最適化でも**キーの性質で正反対の結果**になる (例: fingerprinting は文字列で +、整数で -)。
  だから「固定の正解」ではなく、ノード単位で適応させる。
  ノード単位でできるのは、tag 1バイトでノード種別を切り替えられる設計のおかげ。
* ノード内に閉じた最適化なので、OLC やバッファ管理といった木レベルの仕組みとは独立している。
* 比べるときは **tuple の格納まで含めた比較**が公平だ、という主張も大事。
  ART / HOT の論文は索引本体だけを測っているので、数字をそのまま比べられない。
* Dense leaves は、「正規化キーの末尾4バイト = 整数列」という key normalization の性質に乗っかっている。
  `(文字列, 連番)` のような複合キーにも効く。
* LSM への応用の考察もある: hints は有効、fingerprint は2バイトにするべき、heads は不要、とのこと。
