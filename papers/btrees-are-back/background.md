## 0. ハードウェアの前提

論文の最適化は、ほぼすべて「**キャッシュミスを減らす**」ためのもの。だからまずここを押さえる。

### 0.1 メモリ階層とキャッシュライン

```
レジスタ  <  L1 (32 KiB)  <  L2 (1 MiB)  <  L3 (32 MiB)  <  DRAM  <  SSD
  速い                                                            遅い
```

カッコ内は論文の評価マシン (Ryzen 9 7950X) の1コアあたりの値。

* CPU はメモリを **64 バイトのキャッシュライン単位**で読む。
  1バイトだけ欲しくても 64 バイト運ばれてくるので、**隣にあるデータはタダで読める**。
* L1 ヒットは数サイクル、DRAM まで行くと 100 サイクル以上かかる (桁の感覚として)。
* つまり「比較の回数」よりも「**何本の別々のキャッシュラインに触るか**」で速度が決まりやすい。

**論文との関係**
* heads と hints は、二分探索の比較をスロット配列とヘッダ (=少数のキャッシュライン) の中で済ませるためのもの。
* prefix truncation でノードが密になると、同じキャッシュ量でより多くのキーを抱えられる。

### 0.2 SIMD

1命令で複数のデータを同時に処理する命令 (x86 の SSE / AVX2 など)。

* 例: 16個の1バイト値を一度に「探したい値と等しいか」比較して、結果を16ビットのビットマスクにする。
* 線形探索でも、SIMD を使えば二分探索より速いことがある。分岐がなく、メモリが連続しているから。

**論文との関係**: fingerprinting リーフは、1バイトハッシュの配列を SIMD で線形検索する。ART の Node16 も同じ発想。

### 0.3 分岐予測

CPU は `if` の結果を予想して先に実行しておく。外れると、パイプラインをやり直すので十数サイクル損する。

* 結果がデータ次第でランダムになる `if` (例: 「このスロットは埋まっているか」) は予測が当たりにくい。
* 二分探索も、比較結果がランダムなので分岐予測が苦手な処理。

**論文との関係**: SDL の scan が遅いのは分岐ミスのせい (論文では密度 42% で scan 1回あたり最大30回ミス)。
詳しくは [deep-dive.md](deep-dive.md#5-sdl-の-scan-を-simd-で速くできるか) を参照。

### 0.4 ページと仮想メモリ

* OS はメモリを **4 KiB のページ**単位で管理する。
* プロセスが見るアドレス (仮想アドレス) は、ページテーブルで物理アドレスに変換される。
* 変換結果は TLB というキャッシュに保持される。
* SSD の読み書きもページ単位 (4 KiB) が基本。

**論文との関係**: B-Tree のノードを 4 KiB 固定にしておけば、ノードを丸ごとディスクに追い出したり (evict)、読み戻したりできる。これが「**pageable**」の意味。

### 0.5 malloc のオーバーヘッド

* 小さなオブジェクトを `malloc` で1個ずつ確保すると、アロケータの管理情報や切れ端 (断片化) でメモリが余計にかかる。
* オブジェクト同士がメモリ上でバラバラに散らばるので、局所性も悪い。

**論文との関係**
* インメモリ索引の多くはレコードを個別に確保して、ポインタで指している。
* 論文の Wormhole の分析では、プロセスの使用量の約 1/3 がアロケータのオーバーヘッドだった。
* B-Tree はページ単位で確保し、レコードをページ内に詰めるので、この問題が小さい。

## 1. B-Tree の基本

### 1.1 B-Tree と B+-Tree

**二分探索木の問題点**
* 1ノードに1キーしかないので、木が深くなる (100万件で深さ約20)。
* ノードを1つたどるたびに、メモリ (やディスク) へのランダムアクセスが1回起きる。

**B-Tree (Bayer & McCreight, 1970/1972)** は、1ノードに多数のキーを持たせる。
* 根から葉までの深さはすべて同じ (平衡)。
* ノードが溢れたら2つに分割 (split) し、区切りを親に上げる。

**B+-Tree** は、レコードを**葉だけ**に置く。
* 内部ノードは「どの子に進むか」の区切りキー (separator) だけを持つので、たくさんのキーが入り、木がさらに浅くなる。
* 葉同士を連結すると、範囲検索 (scan) が楽になる。

```
            [ g | p ]                 ← 内部ノード: 区切りキーと子へのポインタ
           /    |    \
   [a b c f]  [g h o]  [p s z]        ← 葉: 実際のレコード
```

**論文との関係**: 論文でいう「B-Tree」はすべて B+-Tree のこと。

### 1.2 fence key (フェンスキー)

ノードが担当するキー範囲の、**下限と上限**。

* 上の図の真ん中の葉は「g 以上 p 未満」を担当する。下限 fence = `g`、上限 fence = `p`。
* fence は親ノードの隣り合う区切りキーと同じ値。それを各ノードにもコピーして持っておく (Graefe の提案)。

**論文との関係**: fence はこの論文のあちこちで使われる。
* prefix truncation で省く接頭辞は「両 fence の共通接頭辞」。
* dense leaves の基準値は下限 fence から決まる。

### 1.3 スロット付きページ (slotted page)

可変長のレコードを固定サイズのページに詰めるための、古典的なレイアウト。

```
 0                                                           4096
 [ヘッダ][slot0][slot1][slot2] →   空き   ← [rec2][rec0][rec1]
          │       │       └──────────────────┘
          │       └──────────────────────────────────┘
          └──────────────────────────────────┘
```

* **スロット**は固定長で、レコードの位置 (offset) と長さを持つ。スロット配列はキー順に並べるので、二分探索できる。
* **レコード本体**はページの末尾側から詰めていく。順番はバラバラでよい。
* 挿入時はスロットを1つずらして差し込む (平均してスロットの半分を移動する)。レコード本体は動かさない。
* 削除してもレコード本体の領域はすぐには回収しない。足りなくなったら詰め直す (compaction)。

**論文との関係**: ベースラインの B-Tree はこれ (論文 Figure 2)。各最適化はこのレイアウトの改造。

### 1.4 split と「waves of misery」

**split** はノードが溢れたときの操作。
* 葉の場合: 中央付近で2つに分け、区切りキーを親に挿入する。親も溢れたら、連鎖的に上へ split が伝わる。
* 内部ノードの場合: 新しい区切りキーは作らず、中央のキーを親に移す。

**Waves of misery** (Glombiewski, Seeger, Graefe, BTW 2019)
* 索引を作った直後は、全ての葉が同じ充填率になっている (例: 90%)。
* その後ランダムに挿入していくと、多くの葉がほぼ同時に満杯になり、**split が一斉に起きる (波)**。
* 一通り split すると、今度は全ての葉が半分程度の充填率でそろい、索引が約2倍に育ったころに次の波が来る。
* 波は繰り返すが、徐々に広がって弱まっていく。

**論文との関係**
* ランダム挿入では葉の充填率が時期によって揺れる。そのため、論文の空間計測は測るタイミングで値がぶれる (4.2節)。
* fan-out の計測では、レコード数を 16^-R (R は 0〜1 の一様乱数) 倍にずらして平均をとり、この揺れを均している (4.4節)。

### 1.5 キャッシュを意識したインメモリ B+-Tree (CSS-Tree, CSB+-Tree)

Rao & Ross (VLDB 1999, SIGMOD 2000)。B-Tree をメモリ上で速くする研究の古典。

* **ノードのサイズをキャッシュライン程度 (数十〜数百バイト) まで小さくする**のが基本方針。ノード内の探索が1〜数本のキャッシュラインで済む。
* **CSS-Tree**: 子ポインタを持たず、配列上の位置計算で子を求める。ポインタがない分キーが多く入るが、更新に弱い (基本的に作り直し)。
* **CSB+-Tree**: あるノードの子をすべてメモリ上に連続して並べ、子ポインタを「先頭の子への1本」だけにする。

**論文との関係**
* 論文はこうした研究を「**ノードを小さくしすぎて、ページングができなくなっている**」としてまとめて退けている (8章)。
* 論文の立場は「ノードは 4 KiB のページのまま、ページの中身の並べ方を工夫して速くする」。この対比を押さえると、論文の狙いがはっきりする。

## 2. キーの表現と圧縮

### 2.1 Key normalization (キーの正規化)

型付きの値や複数列からなるキーを、**`memcmp` (バイト列の辞書順比較) だけで正しく比較できるバイト列**に変換すること (Graefe)。

* 変換は挿入時に1回だけ行う。
* 検索時の比較は「型ごとの比較関数」ではなく単純なバイト比較になり、速く、実装も単純になる。

主な変換規則 (実システムの例。FoundationDB / CockroachDB / PostgreSQL の資料による):

| 型 | 変換 | 理由 |
|---|---|---|
| 符号なし整数 | ビッグエンディアンで書く | 上位バイトが先頭に来ないと辞書順にならない |
| 符号付き整数 | ビッグエンディアン + 符号ビット反転 | 負数を正数より小さく並べるため。-1 → `7F FF FF FF`, 0 → `80 00 00 00` |
| 浮動小数点 | 正なら符号ビット反転、負なら全ビット反転 | IEEE 754 のビット列を全順序に並べ替える |
| 文字列 | `00` を `00 FF` にエスケープし、終端に `00 01` を付ける (CockroachDB 方式) | 複合キーの途中で、次の列とくっつかないようにする |
| NULL | 列の先頭に `00` (NULL) / `01` (非 NULL) のマーカーを付ける | NULL を先頭に並べる |
| 降順 (DESC) | 昇順の変換結果を全ビット反転する | 大小が逆になる |

複合キーの例。`(a INT, s TEXT, id INT DESC)` = `(-1, "ab", 5)` は次のように変換される。

```
a  = -1        → 7F FF FF FF
s  = "ab"      → 01 61 62 00 01     (非NULLマーカー, 'a' 'b', 終端)
id = 5 (DESC)  → ~(80 00 00 05) = 7F FF FF FA
key = 7F FF FF FF 01 61 62 00 01 7F FF FF FA
```

文字列に終端がないと、`("a","bc")` と `("ab","c")` がどちらも `abc` になって区別できなくなる。

**論文との関係**
* 論文の B-Tree はキーを「ただのバイト列」として扱う。整数キーも、正規化済みのバイト列として格納する前提。
* heads はこの正規化済みバイト列の先頭4バイト。
* dense leaves は「正規化キーの末尾4バイト = 整数」とみなせることを利用している。

### 2.2 Poor man's normalized keys (= heads)

Graefe & Larson (ICDE 2001) の手法。**正規化キーの先頭数バイトを、スロットにコピーしておく**。

* 二分探索の多くの比較はスロットだけで決着する。レコード本体 (=別のキャッシュライン) を読みに行かなくて済む。
* 先頭バイトが同じときだけ、本体を読んで比較する。
* 起源はソート (AlphaSort, 1995)。レコード全体ではなく「(キーの先頭, ポインタ)」の組を並べ替えると速い、という発想。
* 共通接頭辞を先に削っておかないと効かない。全キーが `http` で始まるなら、先頭4バイトは全部同じになる。

**論文との関係**: 論文の **heads** はこれそのもの (4バイト)。prefix truncation と組み合わせる理由もここにある。

### 2.3 Prefix B-Trees: prefix truncation と suffix truncation

Bayer & Unterauer (1977) が2種類の圧縮を提案している。

**suffix truncation (区切りキーを短くする)**
* 内部ノードの区切りキーは、左右を分けられさえすればよい。
* 例: 左の最大キー `aeaf`、右の最小キー `aecd` なら、区切りは `aec` で十分 (共通接頭辞 + 1文字)。
* 区切りが短いと内部ノードに多く入り、fan-out が増えて木が浅くなる。

**prefix truncation (ノード内の共通接頭辞を省く)**
* ノード内のキーはすべて fence の共通接頭辞を持つので、それを省いて格納する。

**論文との関係**
* 論文はこの2つを両方使う。
* 区切りキーの選び方は「短くする」流儀に従っているが、「接頭辞を共有させる」方が良いかもしれない、と論文自身が書いている → [deep-dive.md](deep-dive.md#4-区切りキーは短くすべきか接頭辞を共有させるべきか)

### 2.4 Frame-of-reference (FOR) 符号化

Goldstein, Ramakrishnan, Shaft (ICDE 1998)。ページ内の値を「**基準値からの差分**」で持つ圧縮。

```
値:      1005  1009  1002       基準値 1000
格納:       5     9     2       (4ビットずつで足りる)
```

**論文との関係**: dense leaves はこの差分を**配列の添字**として使う。
キー比較なしで `array[key - 基準値]` と一発で引ける。
FOR 自体は既知だが、「差分を配列の添字に使う B-Tree」は文献で見つからなかった、と論文は書いている。

### 2.5 差分圧縮と「B-Tree 圧縮の比較研究」

**差分 (delta) 圧縮**
* 各キーについて、**直前のキー**と共通する接頭辞の長さだけを記録し、残りの部分を格納する。
* LevelDB / RocksDB の SSTable、WiredTiger、MyISAM が採用している。
* そのままでは途中から読めない。そこで K 件ごとに全キーを格納した「restart point」を置き、restart point の上で二分探索してから前方に向かって復元する。

```
restart 0: [共有0][非共有5] "apple"
           [共有5][非共有3] "sau"     → "applesau"
restart 1: [共有0][非共有6] "banana"
```

**Revisiting B-tree Compression** (Gao, Ballijepalli, Wang, SIGMOD 2024)
* 論文が引用しているのはこの SIGMOD 版。SIGMOD 版は読めていないので、以下は同じグループによる VLDB Journal 拡張版の内容。拡張版は「SIGMOD 版と同じ結論」と述べている。
* 7方式 (Head / Tail / Head+Tail / DB2 / WiredTiger / MyISAM / PkB) を比較した。
* 結論: **Head+Tail (= prefix + suffix truncation) が総合的に最良**。差分圧縮は圧縮率が高いこともあるが、展開のコストで遅い。

**論文との関係**
* 論文が差分圧縮を採らない根拠になっている。
* LSM-tree への応用の考察で、「hints は restart point からサンプリングするとよい」と提案している。

## 3. インメモリ索引 (比較対象)

ページングは考えず、「メモリ上で最速」を狙った構造たち。論文の6章で比較されている。

### 3.1 Trie (トライ) / 基数木の基本

キーを先頭から少しずつ (例えば1バイトずつ) 切り出し、その値で子を選ぶ木。

```
キー: "and", "ant", "dog"
       (root)
       /    \
      a      d
      |      |
      n      o
     / \     |
    d   t    g
```

* **span**: 1段で消費するビット数。8なら1バイトずつ進む。span が大きいほど木は浅いが、子の配列 (2^span 個) が疎になって無駄が増える。
* 深さは**キーの長さ**で決まり、キーの件数には依存しない。
* キー比較が不要で、回転などの再平衡もいらない。
* **path compression**: 子が1つしかないノードの連鎖を1つにまとめる (Patricia trie)。
* **lazy expansion**: 他のキーと区別する必要が出るまで、下のノードを作らない。

lazy expansion などを使うと、たどった経路からキー全体が復元できなくなる。そのため、**最後に本物のキーと照合する必要がある**。

### 3.2 ART (Adaptive Radix Tree)

Leis, Kemper, Neumann (ICDE 2013)。span は8ビットに固定し、**子の数に応じてノードの形を4種類から選ぶ**基数木。

| 種類 | 子の数 | 中身 | サイズ |
|---|---|---|---|
| Node4 | 2〜4 | キー1バイト×4 (ソート済み) + ポインタ×4 | 52 B |
| Node16 | 5〜16 | キー1バイト×16 + ポインタ×16 | 160 B |
| Node48 | 17〜48 | 256要素の添字表 (1バイト) + ポインタ×48 | 656 B |
| Node256 | 49〜256 | ポインタ×256 (バイト値で直接引く) | 2064 B |

```
Node16:  [hdr][k0 k1 ... k15][p0 p1 ... p15]
  検索: 探すバイトを16個に複製 → SIMD で一斉比較 → ビットマスクの最下位ビット = 位置
Node48:  [hdr][idx[0..255]][p0 ... p47]
  検索: idx[バイト値] → p[その値]  (2回の配列参照)
```

* 経路の圧縮は、ノードに最大8バイトまで持つハイブリッド方式。それより長い分は読み飛ばし、最後に葉で検証する。
* 値はタプル ID (8バイト) を子ポインタの位置に直接埋め込める。そのため二次索引向き。
* 葉で検証するには、タプル ID から**キー全体を取り出せる**必要がある。
* キーは 2.1 の正規化済みバイト列であることが前提 (ART 論文でも同様の変換を述べている。浮動小数点の扱いなど細部は異なる)。

**論文との関係**
* 論文では、tuple を別に確保してポインタを持たせる形で比べている。
* 整数の lookup では ART が最強 (sparse で適応型 B-Tree の 2.29 倍)。文字列では ART の方が適応型 B-Tree より 34〜37% 遅く、ベースライン B-Tree と同程度。
* scan では B-Tree が圧勝。trie は1回の scan で多数のノードを渡り歩くため。

### 3.3 HOT (Height Optimized Trie)

Binna, Zangerle, Pichl, Specht, Leis (SIGMOD 2018)。

ART は span 固定なので、キーが疎だと下の方のノードの子が少なくなり、木が深くなる。
HOT は逆に、**fan-out の上限を固定 (k=32) し、span をデータに合わせて変える**。

* 2分木の Patricia trie の節を、最大32個の子を持つ「複合ノード」にまとめる。
* 各ノードは「キー同士を区別するのに実際に使うビット位置 (discriminative bits)」だけを見る。
* 検索手順:
  1. PEXT 命令 (指定ビットだけ抜き出す命令) で、探索キーから該当ビットを一度に取り出す。
  2. ノード内の部分キー群と SIMD で比較する。
* ノードの物理形式は9種類 (64〜472 バイト)。

**論文との関係**
* 文字列の lookup は適応型 B-Tree とほぼ同等 (HOT の方が 5% 速い〜14% 遅い)。
* 論文は、HOT の原論文が自分に有利な測り方をしていたことを指摘している。tuple の取得を省いていたこと、64ビットの整数キーを使っていたこと、などで、条件をそろえると ART より 39% 遅い。

### 3.4 Masstree

Mao, Kohler, Morris (EuroSys 2012)。**キーを8バイトずつ切り、各層を B+-Tree にした trie**。

* 1層目はキーの 0〜7 バイト目、2層目は 8〜15 バイト目、…と担当する。
* 各層では8バイトを整数として比較する (ビッグエンディアンなら、辞書順と一致する)。
* 長い共通接頭辞は trie の層で吸収し、各層の中は B+-Tree で並行性に強い。

**論文との関係**: Wormhole より大幅に遅いので、比較対象から外したとだけ書かれている。

### 3.5 Wormhole

Wu, Ni, Jiang (EuroSys 2019)。**B+-Tree の内部ノードを「接頭辞のハッシュ表」に置き換えた**構造。

* 葉はソート済みの連結リスト。各葉に「anchor key」(その葉の範囲を代表する短い接頭辞) を持たせる。
* 全 anchor の trie を作り、その各節点をハッシュ表に入れる (MetaTrieHT)。
* 検索は「**接頭辞の長さで二分探索**」する。
  `key[0:mid]` がハッシュ表にあれば長い側へ、なければ短い側へ進み、最長一致する接頭辞を見つけたら、そこから葉を特定する。
* 計算量は O(log キー長)。件数 N に依存しない。
* 葉の中は 16ビットのハッシュタグ配列で探す (fingerprinting と似た発想)。
* レコード本体は葉に入れず、ポインタで持つ。

**論文との関係**
* 論文の **Figure 1 の比較相手**であり、最大のライバル。
* lookup: ベースラインは 53〜60% 遅い。適応型でも 26〜28% 遅いが、dense では 27% 速い。
* scan: 適応型 B-Tree が 88〜430% 速い。レコードがポインタ経由なので、Wormhole は局所性が悪い。

### 3.6 LITS (Learned Index for Strings)

Yang & Chen (2024)。**学習済みモデルで「キーが配列のどこにあるか」を予測する** learned index の文字列版。

* 学習済み索引の発想: キーの累積分布 (CDF) をモデルで近似すれば、位置を計算で求められる。
* LITS は HPT (Hash-enhanced Prefix Table) を使う。「ある接頭辞の次に来る文字」の分布を表にしたもので、これで CDF を推定する。
* 予測が衝突した部分は子ノードを作って再帰する。キーが偏っている部分は HOT に任せる。
* 構築時に与えたサンプルで学習するので、**分布が変わると性能が落ちる**。

**論文との関係**
* urls では適応型 B-Tree が 42% 速く、wiki では同等。整数では LITS の方が速い。scan では B-Tree の方が速い。
* 学習用に渡すキーを 50% から 5% に減らすと、LITS のスループットは -69%〜+41% と大きく変わる。

### 3.7 TLX の B+-Tree (旧 STX B+ Tree)

C++ のテンプレートで書かれた汎用 B+-Tree。

* `key_type slotkey[N]` のように、**キーを固定サイズの配列に入れる**。N は `sizeof(key_type)` から決まる (ノード 256 バイト目安)。
* 文字列のような可変長キーは、`std::vector` (24バイトのハンドル) を介してヒープを指すしかない。
  そのため比較のたびにポインタをたどることになる。
* Rust の `BTreeMap` や Google の btree も、同じくジェネリックな作り。

**論文との関係**: 「よく使われる汎用 B-Tree は遅い」(Insight 6)。文字列では適応型 B-Tree が 2.5〜3.6 倍速い。

## 4. 別系統の木構造

### 4.1 FPTree

Oukid et al. (SIGMOD 2016)。**不揮発メモリ (persistent memory / SCM) 用の B+-Tree**。

* SCM への書き込みは高くつく。永続化のためにキャッシュラインを明示的にフラッシュする必要があるため。
  ソート済みの葉に挿入するとエントリを大量にずらすことになり、書き込みが多い。
* そこで**葉をソートしない**。空いたスロットに書き、有効スロットをビットマップで示す。
* ソートしない代わりに、**キーの1バイトハッシュ (fingerprint)** を葉の先頭のキャッシュラインに並べる。
  検索はまず fingerprint を走査し、一致したものだけ本体を比べる。期待される本体比較は約1回。
* 内部ノードは DRAM に置き、再起動時に作り直す (selective persistence)。

**論文との関係**: 論文の **fingerprinting リーフ**はこれを DRAM 向けに持ってきたもの。
scan の前に遅延ソートする点、sorted 部分と unsorted 部分に分ける点は論文側の工夫。

### 4.2 Bw-Tree

Levandoski, Lomet, Sengupta (ICDE 2013)。**ロックを使わない (latch-free) B-Tree**。

* ノードを直接指さず、**mapping table** (論理ページ ID → 物理アドレス) を経由する。
* 更新はノードを書き換えず、「差分レコード (delta)」を連結リストの先頭に付け足す。
  付け足しは mapping table への CAS 1回で済む。
* delta が溜まったら、新しいノードにまとめ直す (consolidation)。

その後の検証論文 (Wang et al., SIGMOD 2018 "Building a Bw-Tree Takes More Than Just Buzz Words") の結論:
* 改良版の OpenBw-Tree でも、**楽観的ロックカップリング (OLC) の普通の B+-Tree より遅い**。
* mapping table の参照と delta chain の走査がキャッシュミスを生む。lock-free が常に得とは限らない。

**論文との関係**: 「ページ内で普通に書き換える B-Tree + OLC」でよい、という判断の根拠。

### 4.3 BP-Tree

Xu et al. (VLDB 2023)。

* 点検索に最適なノードサイズは小さく、範囲検索に最適なサイズは大きい。このトレードオフを解こうとした構造。
* 葉だけ大きくし、その中身を「未ソートのログ + ソート済みの見出し + 未ソートのブロック群」にする。

**論文との関係**: 固定長キー専用なこと、スロット配列に移植すると find がキャッシュ非友好的になること、大きな葉はページングに不利なこと、を理由に採用していない。

### 4.4 LSM-tree

O'Neil et al. (1996)。

* 書き込みはまずメモリ上のソート済み構造に溜め、一杯になったらディスクに**変更不能なソート済みファイル**として書き出す。
* ファイル同士は裏でマージ (compaction) する。
* 書き込みはシーケンシャルで速い (write amplification が小さい) が、読み出しは複数のファイルを見る必要がある。
* RocksDB, LevelDB, Cassandra などが採用している。

**論文との関係**: 論文の最適化を LSM に移すならどうなるか、を考察している。
* hints は有効。
* fingerprint は2バイトにすべき (誤一致すると高価な展開が発生するため)。
* heads は割に合わない。
* fully dense leaves は値の圧縮と両立しない。

## 5. ストレージエンジン側の仕組み

「メモリに収まる間はインメモリ並みに速く、溢れたら SSD に逃がす」ための仕組み。論文の B-Tree は、この上に載ることを前提にしている。

### 5.1 古典的なバッファマネージャ

ディスク上のページをメモリにキャッシュする層。

```
fix(pid):                      ← ページを使う前に必ず呼ぶ
  ハッシュ表のロックを取る
  frame = table[pid]           ← ページ ID → メモリ上の位置
  なければ: 追い出し候補を選ぶ → ディスクから読む → 登録
  pin_count++                  ← 使用中なので追い出すな
  LRU 等の統計を更新
  ロックを外す
```

* データ構造は、子ノードを「ページ ID」で指す。たどるたびに上の処理が走る。
* 全データがメモリに載っていても、毎回ハッシュ表を引くことになる。
  Harizopoulos et al. (SIGMOD 2008) の計測では、命令数の約3割がバッファ管理だった。
* ハッシュ表のロックや pin カウンタは全スレッドが書き込むので、キャッシュラインの奪い合いも起きる。

### 5.2 Pointer swizzling と LeanStore

Graefe et al. (VLDB 2015) と LeanStore (Leis et al., ICDE 2018)。

* 子への参照 (**swip**, 8バイト) に、メモリ上にあるときは**ポインタそのもの**、ディスク上にあるときは**ページ ID**を入れる。どちらかは1ビットのタグで区別する。
* メモリ上のページへのアクセスは「1ビット確認してポインタをたどる」だけで済み、ハッシュ表が要らない。
* 追い出し:
  1. ランダムに選んだページの swip を、ページ ID に戻しておく (cooling)。
  2. しばらくアクセスされなければ追い出す。アクセスされたらポインタに戻す (Second Chance 方式)。
* 制約: 各ページを指す swip は**ちょうど1つ**だけ (木構造なら自然に満たされる)。
  子がメモリ上にある内部ノードは追い出せない。追い出すと、ポインタがディスクに書かれてしまうため。

**LeanStore の B-Tree** はスロット付きページで、fence、prefix truncation、heads (先頭4バイト)、**hints** (16個) を持つ。
論文のベースラインと最初の3つの最適化は、ほぼこれと同じ。→ hints の詳細は [deep-dive.md](deep-dive.md#3-hints-の原典と実装)

### 5.3 vmcache

Leis et al. (SIGMOD 2023)。**仮想メモリでページ ID → アドレス変換をさせる**バッファマネージャ。

```
仮想アドレス空間 (巨大に予約, mmap)
[page 0][page 1][page 2] ... [page N]
   ↑ ページ ID p のアドレスは常に  base + p × 4KiB
   物理メモリが割り当たっているのは、キャッシュ中のページだけ
```

* 起動時に、全ページ分の仮想アドレス空間を予約しておく。
* ページ ID からアドレスへの変換は**足し算1回**。変換そのものは OS のページテーブルが担当する。
* swizzling のような「ポインタか ID か」の区別が不要。swip を1つに限る制約もない。
* 追い出し:
  1. ページを (汚れていれば) SSD に書く。
  2. `madvise(MADV_DONTNEED)` で物理メモリだけ返す。仮想アドレスは残る。
* ページごとに 64ビットの状態語 (状態8ビット + バージョン56ビット) を持つ。
  これがそのまま次節の OLC のロック兼バージョンになる。
* 大規模に使うと Linux のページテーブル操作がボトルネックになる。そのため、専用カーネルモジュール exmap も提案されている。

**論文との関係**
* 論文の B-Tree は固定 4 KiB ノードなので、**データ構造を一切変えずに** vmcache に載った (7章)。
* マルチスレッド評価と、メモリ溢れの評価はこの上で行っている。

### 5.4 ロックカップリングと楽観的ロックカップリング (OLC)

**ロックカップリング (crabbing)**
* 木を下るとき「子のロックを取ってから親のロックを外す」。保持するロックは常に2つまで。
* 問題: 読み取りでも共有ロックを取るとロック変数に**書き込み**が発生する。根のロックのキャッシュラインを全コアで奪い合い、読むだけなのにスケールしない。

**OLC** (Leis, Haubenschild, Neumann, IEEE Data Eng. Bull. 2019)
* 各ノードのロックに**バージョン番号**を持たせ、書き手は変更のたびにバージョンを1つ増やす。
* 読み手はロックを取らない。

```
v = node.version を読む (ロック中ならやり直し)
ノードを読む (書き換え中のゴミを読むかもしれない)
child = 子ポインタ
node.version == v か確認 → 違えば最初からやり直し    ← 子をたどる前に必ず検証
次は child で同じことを繰り返す
```

* 読み手は何も書かないので、キャッシュラインの奪い合いが起きない。
* ノード内の探索は、途中でゴミを読んでも**必ず終了する**ように書く必要がある (無限ループすると検証にたどり着けない)。
* 解放したノードを読まれないように、エポックベースの回収などが別途必要。

**論文との関係**
* 論文の最適化はすべて「ノードの中」の話なので、OLC (木全体の同期) とは独立している (直交)。
* ただし dense leaves は操作自体が速すぎて、ロック処理のオーバーヘッドが相対的に目立つ。そのためマルチスレッドでは速度向上が小さくなる。

### 5.5 Contention split と XMerge

Alhomssi & Leis (CIDR 2021)。

**Contention split**
* ロックはページ単位なので、別々のホットなキーが同じ葉にあると、無関係なのに奪い合いになる。
* 更新時に「ロックをすぐ取れたか」を確率的にサンプリングしておく。
* 競合が多く、しかも別のキーへの更新同士だったら、**満杯でなくても**その2つのキーの間で split する。

**XMerge**
* 隣り合う X 個のノードの空きを合計して1ノード分以上あれば、X-1 個に詰め直す。
* 可変長キーの B-Tree は充填率が下がりやすいので、その対策。

**論文との関係**
* 論文は contention split を fingerprinting リーフに実装した (7.3節)。
* 書き込みの 1/30 以上が競合したら split する。これでページサイズを大きくしても書き込み性能が落ちなくなる。

### 5.6 最近の NVMe の性能

Haas & Leis (VLDB 2023)。

* PCIe 4.0 の SSD 8台で、ランダム 4 KiB 読み出しが **約1250万 IOPS**。
* 現状のDBMSはこの性能を使い切れていない。そこで、I/O 側を工夫すると、CPU (索引の処理) が律速になる。

**論文との関係**: 「SSD に溢れる状況でも索引の CPU 性能が重要」という動機の根拠 (1章)。

## 6. ベンチマークの道具

### 6.1 YCSB

Cooper et al. (SoCC 2010)。クラウド向け KV ストアの標準ベンチマーク。

| ワークロード | 内容 |
|---|---|
| A | 読み 50% / 更新 50% |
| B | 読み 95% / 更新 5% |
| C | 読み 100% |
| D | 読み 95% / 挿入 5% (最近のものほど読まれる) |
| E | **scan 95% / 挿入 5%** (scan の開始位置は Zipf、長さは一様分布) |
| F | 読み 50% / read-modify-write 50% |

**論文との関係**
* lookup のキーは YCSB にならって Zipf (α=0.99) で選んでいる。scan の長さは 1〜50 の一様分布。
* fingerprinting リーフの評価には YCSB-E を使っている。

### 6.2 Zipf 分布

k 番目に人気のあるキーが選ばれる確率が、**1/k^α に比例する**分布。少数のキーにアクセスが集中する。

100万キー、α=0.99 の場合の集中度 (手元で計算した値):

| 上位何件 | アクセスの割合 |
|---|---|
| 1 件 | 6.5% |
| 10 件 | 19% |
| 1,000 件 (0.1%) | 50% |
| 100,000 件 (10%) | 83% |

**論文との関係**
* α を大きくするほどホットなキーがキャッシュに残り、どの構造も速くなる (6.6節)。
* ただし伸び方は構造によって違う。ART / TLX / Wormhole は伸びが大きく、HOT はプリフェッチに頼っているので伸びが小さい。
