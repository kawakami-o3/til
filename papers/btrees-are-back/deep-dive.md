## 1. Key normalization の具体的なやり方

### 何をするか

型付きの値の組 (タプル) を、`memcmp` の大小がそのまま元の値の大小になるバイト列に変換する。
変換規則は [background.md 2.1](background.md#21-key-normalization-キーの正規化) の表のとおり。

ここで押さえたいのは、各規則が「**辞書順比較の性質**」に合わせた結果だということ。

* 辞書順は**先頭バイトから**比べる。
  → 整数はビッグエンディアンにする。リトルエンディアンだと最下位バイトから比べてしまう。
* 辞書順は各バイトを**符号なし**として比べる。
  → 2の補数の負数は先頭ビットが1なので正数より大きく見える。そこで符号ビットを反転する。
* 辞書順では「短い方が接頭辞なら、短い方が小さい」。
  → 可変長の列の後ろに別の列が続くと境界が分からなくなる。そこで終端記号を付ける。
  終端記号が値の中に出てきたら困るので、値の中の `00` はエスケープする。

### 論文の B-Tree が正規化に頼っている箇所

1. **比較がすべて `memcmp`**。
   `BTreeNode::lowerBound` (`btree/btree2020.cpp`) は、head が等しいときに `memcmp` で比べ、それでも同じなら長さで比べるだけ。型の知識を持たない。
2. **heads**。
   `head()` (`btree/btree2020.hpp:71`) は、キーの先頭4バイトを `__builtin_bswap32` でビッグエンディアンとして読んで、`uint32_t` にする。
   これで「整数としての大小 = 先頭4バイトの辞書順」になる。4バイト未満のキーは、下位を0で埋める。
3. **dense leaves**。
   正規化済みの複合キーは「各列の正規化結果を連結したもの」。だから**最後の列が整数**なら、キーの末尾4バイトがその整数になる。
   論文はこの末尾4バイトを「数値部 (numeric part)」と呼び、基準値との差を配列の添字にする。

例えば `(テーブル名 TEXT, id INT)` という複合キーなら、同じテーブル名の範囲内では末尾4バイトだけが変わる連番になる。これが dense leaf にぴったり合う。

### 注意点

* 正規化キーから元の値には戻せないことがある (文字列の照合順序キーなど)。
* 正規化キーは元より長くなることがある。ICU の照合キーはラテン文字で約1.5倍 (PostgreSQL wiki の見積もり)。
* 符号付き整数でも、符号ビットを反転してあれば、末尾4バイトの差はそのまま値の差になる。
  dense leaves は数値部を符号なし整数として引き算するが、問題にならない。

## 2. OLC と vmcache の仕組み

### OLC の要点

詳しくは [background.md 5.4](background.md#54-ロックカップリングと楽観的ロックカップリング-olc)。

* 読み手はロックを取らずにバージョン番号を読む。読み終わってからバージョンが変わっていないか検証し、変わっていたらやり直す。
* 子ポインタは、**親の検証が通ってから**たどる。

### vmcache の要点

詳しくは [background.md 5.3](background.md#53-vmcache)。

* ページ ID p のアドレスは常に `virtMem + p`。ポインタの書き換え (swizzling) が要らない。
* ページごとの 64ビット状態語 `stateAndVersion` は、上位8ビットが状態、下位56ビットがバージョン。
  状態の値は次のとおり。
  * 0: Unlocked
  * 1〜252: 共有ロック中の読み手の数
  * 253: Locked
  * 254: Marked (追い出し候補)
  * 255: Evicted
* 読み手 (`GuardO`) はこの語を読んでおき、後で `checkVersionAndRestart` で検証する。

### 2つがかみ合う点

1. **「追い出された」も「書き換えられた」も、バージョンの変化として検出できる**。
   追い出し時にもバージョンが進む。だから楽観的に読んでいたページが途中で追い出されても、検証で失敗してやり直すだけで済む。
   「ロックの検証」と「まだメモリにあるかの確認」が1回のチェックに統合されている。
2. **子の参照がただのページ ID で済む**。
   LeanStore の swizzling では、「子がメモリ上にある内部ノードは追い出せない」「参照元は1つだけ」といった制約があった。vmcache ではこれがない。
   B-Tree 側は、子ポインタの代わりにページ ID を入れるだけでよい。
3. **ノードが固定サイズのページ**なので、B-Tree のコードはページの中身だけを気にすればよい。
   論文が「データ構造を一切変えずに統合できた」と書けるのはこのため。

### 論文の最適化が「直交」と言える理由と、例外

* heads、hints、fingerprint、dense はすべて、1ページの中のバイト配置の話。どのページをいつロックするかという木レベルの話には関与しない。
* ただし OLC では、ページ内の探索が**書き換え中の中途半端なデータを読んでも暴走しない**ことが前提になる。
  例えば二分探索の範囲が壊れて無限ループすると、検証にたどり着けない。
  hints による範囲の絞り込みも、壊れた値を読んだときに範囲外へ出ないように書く必要がある。
  これは論文には書かれておらず、btree24 リポジトリでの扱いは未確認。
* 論文が挙げている例外: dense leaves は1回の操作が非常に速いので、ロック処理のオーバーヘッドの比率が上がり、マルチスレッドでは速度向上が縮む (7.1節)。

## 3. hints の原典と実装

### 原典

The Evolution of LeanStore (Alhomssi, Haubenschild, Leis, BTW 2023)。

* hint 数は16で、各 hint は4バイトの head なので、ちょうど64バイト = **1キャッシュライン**に収まる。
* hint 同士の間隔は `#slots ÷ (#hints + 1)` で一定。
* 論文はこれを「ページ内のマイクロ索引」と呼んでいる。

### 実装 (`btree/btree2020.cpp`)

**作る (`makeHint`)**

```cpp
dist = count / (hintCount + 1);
for (i = 0; i < hintCount; i++)
   hint[i] = slot[dist * (i + 1)].head[0];
```

`count` 個のスロットを17等分し、その境目にあるスロットの head をコピーする。

**探す (`searchHint`)**

```cpp
if (count > hintCount * 2) {          // スロットが32個以下なら hints を使わない
   dist = count / (hintCount + 1);
   pos  = 最初に hint[pos] >= keyHead となる位置
   pos2 = pos 以降で最初に hint[pos2] != keyHead となる位置
   lower = pos * dist;
   if (pos2 < hintCount) upper = (pos2 + 1) * dist;
}
// この後 [lower, upper) で head を使った二分探索
```

* 実装は hints を線形走査している。LeanStore の論文は「二分探索」と書いているが、どちらにせよ触るのは1キャッシュラインだけなので、キャッシュミスの面では差がない。
* **`pos2` があるのは、head が同じキーが続く場合のため**。
  例えば urls のように多くのキーが同じ4バイトで始まると、複数の hint が `keyHead` と等しくなる。
  そのときは等しい hint の範囲全体を、探索範囲に含める必要がある。
  論文で「hints は文字列ではほぼ効かない (urls では絞り込み後も全体の30%が残る)」とあるのは、この状況。

**更新 (`updateHint`)**

```cpp
dist = count / (hintCount + 1);
begin = 0;
if (count > hintCount*2 + 1 && (count-1)/(hintCount+1) == dist && slotId/dist > 1)
   begin = slotId / dist - 1;     // 間隔が変わらないなら、挿入位置より後ろだけ更新
for (i = begin; i < hintCount; i++) hint[i] = slot[dist*(i+1)].head[0];
```

挿入でスロットが1つずれると、挿入位置より後ろのサンプル位置の中身が変わる。
間隔 `dist` が変わらなければ後ろ側だけ直せばよく、変わったら全部作り直す。論文の説明どおり。

### 効く条件の整理

* hints が効くのは、**head が値ごとにバラけているとき** (整数キー: lookup +25〜26%)。
* 挿入のたびに更新が要るので、文字列の insert ではわずかに遅くなる (命令数 +20%)。
* 空間コストは64バイト/ページ (1.5〜2%) と小さい。論文は「insert が中心でなければ入れるべき」としている。

## 4. 区切りキーは短くすべきか、接頭辞を共有させるべきか

> 論文2章: 区切りキーは短くするのが通例だが、prefix truncation に使うことを考えると「隣の区切りキーとの共通接頭辞を最大化する」方が良いかもしれない。ただし本論文は通例に従う。

論文自身が結論を出していないので、以下は**実装の挙動の確認と、自分の考察**。

### 実装が実際にやっていること (`BTreeNode::findSeparator`)

`USE_ORIGINAL = false` 側のコードが使われている。

* **内部ノード**: ちょうど真ん中 (`count/2 - 1`) で分割する。区切りキーを短くする工夫はない。
* **葉**の手順:
  1. 中央付近の窓 `[count/2 - count/32, count/2 - count/32 + count/16]` (全体の 1/16 の幅) をとる。
  2. 窓の両端のキーの共通接頭辞の長さ `rangeCommonPrefix` を求める。
  3. 窓の先頭から順に、`rangeCommonPrefix` 番目のバイトが先頭キーと**違う最初のキー**を探す。
  4. そのキーの先頭 `rangeCommonPrefix + 1` バイトを区切りキーにして、その手前で分割する。

つまり「中央付近の窓の中で、最も短い区切りキーが作れる位置で分ける」。論文の記述 (count/16 個の範囲、最初に異なるキー) と一致する。

### 2つの方針のトレードオフ (自分の考察)

前提として、子ノードの prefix は「自分の下限 fence と上限 fence の共通接頭辞」で決まる。そして fence は区切りキーそのもの。

**短い区切りキーの利点**
* 内部ノードに入る区切りキーが増え、fan-out が上がって木が浅くなる。
* 区切りキー同士の比較も短くて済む。

**短い区切りキーの欠点**
* 区切りキーを途中で切ると、**隣の fence との共通接頭辞まで短くなる**ことがある。
* 例: 葉の範囲がもともと `abcd1` 〜 `abcd5` だったとする。
  * 下限 fence を短く切って `abc` にすると、子の prefix は `abc` (3バイト) になる。
  * 切らずに `abcd1` のままなら、prefix は `abcd` (4バイト) を共有できる。
* その結果、その葉の全キーが1バイトずつ長く格納され、heads の4バイトのうち1バイトが「全キーで同じ値」に浪費される。

**どちらが効くかの見立て**
* 内部ノードは全ノードの数%以下しかない (fan-out が数十〜数百のため)。区切りキー長による fan-out の差は、木の高さにはほとんど響かない。
* 一方、葉の prefix が1〜2バイト伸びると、**全レコード**の格納サイズと heads の識別力に効く。
* 論文の実測でも、heads の効き目は「先頭バイトでキーが区別できるか」で大きく変わった (urls 38% vs wiki 61%)。

ここから、**葉の fence については、接頭辞の共有を優先する方が得をする場面が多いのでは**、と考えている。
ただし次の点で、結論は出せない。

* 葉の fence も、親から見れば区切りキー。fence を長くすれば親の fan-out は下がる。
* 窓の中で分割位置を動かすと、左右の葉の件数バランスも変わる。
* 実測がない。btree-cpp の `findSeparator` を差し替えて urls / wiki で測るのが、一番手早い確かめ方。

### 補足: dense leaves 用の分割

`DenseNode::densifySplit` (`btree/dense.cpp`) は別ロジック。
* 「下側のノードを dense にできる最大の分割点」を探し、それが中央以上なら採用する。
* 区切りキーは「次のキーより1小さい値」を作って使う (末尾バイトを1減らし、足りない桁は `FF` で埋める)。

ここでは区切りキーの短さよりも、dense 化できることを優先している。

## 5. SDL の scan を SIMD で速くできるか

> 論文4.6節: SDL の scan は密度が低いと最大9%遅くなる。分岐ミスが原因 (密度42%で scan 1回あたり最大30回)。SIMD を使えば大幅に減らせるだろう。

論文は今後の課題としている。以下は**実装の比較と、自分の案** (未計測)。

### FDL と SDL の scan の書き方の違い (`btree/dense.cpp`)

`named-configs` を見ると、`dense1` = FDL、`dense2` = SDL。

**FDL (`range_lookup1`): 存在ビットマップを使う**

```cpp
word = mask[wordIndex] >> shift;
while (true) {
   tz = countr_zero(word);         // 次に立っているビットまで一気に飛ぶ
   if (tz == 64) { 次のワードへ; continue; }
   entryIndex = ...;               // 見つかったレコード
   callback(...);
   word >>= tz + 1;
}
```

**SDL (`range_lookup2`): スロットを1つずつ見る**

```cpp
for (i = firstIndex; i < slotCount; ++i) {
   if (slots[i]) {                 // ← スロットごとにデータ依存の分岐
      callback(...);
   }
}
```

### なぜ SDL だけ分岐ミスが多いのか

* SDL の `if (slots[i])` は、空きスロットと埋まったスロットがランダムに混ざると、予測がほぼ当たらない。
  当たりにくさは「埋まっている確率」が 50% 付近で最大になる。論文の「42%で最大」はこれと整合的。
* FDL は空きスロットを `countr_zero` で**まとめて読み飛ばす**。分岐は「次のレコードがあるか」の1種類だけで、空きスロットの数に依存しない。
  論文の「FDL は最大でも 11 回/scan」もこれで説明がつく。

### 改善案 (自分の考察)

**案A: SIMD で「非ゼロのスロット」のビットマスクを作る**
* AVX2 で 16個の `uint16_t` スロットを一度に読み、ゼロと比較して、`movemask` で16ビットのマスクにする。
* あとは FDL と同じく `countr_zero` で立っているビットだけを回る。
* ページ内のスロットは高々千数百個なので、1 scan あたり数十〜百回程度の SIMD 比較で済む。
* SDL のレイアウトは変えずに済む。

**案B: SDL にも存在ビットマップを持たせる**
* 1000スロットで125バイト (ページの約3%) を追加する。
* scan は FDL と同じコードになる。ただし挿入・削除のたびにビットも更新する必要がある。

案A の方が、レイアウトを変えずに済むので筋が良いと思う。

ただし、論文の適応型 B-Tree は SDL を選択肢に入れていない (比較ベース / fingerprinting / FDL の3種類)。
**SDL の scan を速くしても、公開されている適応型 B-Tree の性能は変わらない**。

それでも SDL を速くする意味はある。論文の Figure 9 によると、SDL が FDL より有利な場面があるため。
* 中程度の密度: lookup が 10% 速くなるのは、SDL なら密度 28%、FDL は 44% から。FDL が SDL を追い越すのは密度 58%。
* 値が大きい場合: 空きスロットのコストが小さいので、SDL に有利。
* 値が可変長の場合: FDL は使えない。

scan の弱点が消えれば、SDL を適応型の選択肢に加える根拠になりうる。
